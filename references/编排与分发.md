# 编排与分发（分批开工前必算）

> **为什么固化**：分发前要算清「每本书怎么编排更合理」。之前几本书的分批（4 个 agent / 32 个 agent）都是**拍出来的**，没有一把尺子。本文件是那把尺子。
> **它在开工后、批量前跑，产出「几个 agent、每个装哪几章」**。

## 一、先算容量：三笔账

| 账 | 怎么算 | 实测值（英语商业书） |
|---|---|---|
| **源文** | 英文字符 ÷ 4 | 某商业书 68,589 字符 → 17,198 token |
| **译文** | 中文字 × 0.6～1.0（**上界按 1.0 算**） | 27,457 中文字 → 27,457 token（上界） |
| **固定开销** | vault 规则 + 工具 schema + 规范/术语切片 + 往返 | **≈ 2–3 万 token / agent** |

**换算速查：约 2.6 token / 英文词**（源 + 译合计）。拿源文词数 × 2.6，就是这本的全部上下文占用。

命令：`python scripts/estimate_cost.py --book-dir <书>` 出源文侧；译者产出后回填译文侧。

## 二、先用窗口算一次，再看容量是不是约束

先跑 `python scripts/plan_batches.py --book-dir <书> --context-window <模型窗口>`。它按「源文 token + 译文 token + 固定开销」算每批能装几章，并按 3 万中文字上限封顶。

小书（如 1.7 万词商业书）会显示一批就够，这时容量不是分批理由；大书、小窗口、长文连载才按窗口切批。

- 一本 1.7 万词的商业书 ≈ **44,700 token = 1M 窗口的 4.5%**；
- 11 本合计 10.7 万词 ≈ **28.6 万 token = 28.6%**。

所以「窗口装得下」不等于「应该塞满」；但窗口装不下、或模型窗口较小时，必须按 `plan_batches.py` 的预算切。

## 三、真正的三条尺子

1. **上下文预算**：单批 `源文 + 译文 + 固定开销` 不超过窗口的 80%；`plan_batches.py` 直接给批次。
2. **质量衰减**：上下文里堆到几十万字后，指令遵循与风格一致性会掉，且**掉在哪一章不可预测**——不是「装不下」，是「变了味」。
3. **失败成本**：一个 agent 译到第 8 章崩了，前面 7 章要重跑；产出越多，单点失败越贵。

**落点：单 agent 产出 ≤ 2.5–3 万中文字**（≈ 一本商业书）。这个数是从「一本一 agent 质量可接受」反推的，不是容量上限。

> 反例参照：早期某书按 1 章/agent 跑了 32 个 agent，把 2–3 万 token 的固定开销重复了 32 次——**省错了地方**。

## 四、配对方法（多本一批时）

1. 逐本量出「预估中文字」（`source_en/` 词数 × 1.6）；
2. **首尾配对**（最大配最小），使各 agent 的产出尽量齐；
3. 超出尺子的那本（如《Closing》27.5k 逼近上限）**单跑**，不硬配；
4. 奇数本时，多出来的那本与次小的一本合并，或单跑。

**实例（11 本同构小书，2 本/agent）**：

| agent | 书 | 中文字 |
|---|---|---|
| 1 | Closing（单跑，试点） | 27,504 |
| 2 | Lead Nurture + GOATed Ads | 29,393 |
| 3 | Branding + Proof Checklist | 24,112 |
| 4 | Price Raise + Lifetime Value | 22,729 |
| 5 | Retention + Hooks | 22,812 |
| 6 | Fast Cash + Marketing Machine | 23,114 |

区间 22.7–29.4k，除试点外很齐。

## 五、分发时的三条纪律

- **逐文件核验，不看 agent 的汇总**：一个 agent 领了 6 章，可能静默只写 5 章。核对：文件数、每文件字数、`<!-- 本章翻译完成 -->` 标记，三者缺一即返工。
- **同一本书同一天跑完**：跨天会掉 prompt 缓存前缀（成本按未命中重算）。
- **先 1 章 / 1 本做基准**，再按上面的配对铺开；基准那本的结果同时校准「≤2.5–3 万中文字」这条尺子。
- **prompt 里的路径占位符必须逐个换成真实路径再发**：发之前拿「`{`」搜一遍；同一批多个 agent 各自手写路径时逐个核。写法示例见 `references/executor-prompt-templates.md`。

## 六、合章与分章的取舍

- **合章**（一个 agent 多章）：省掉重复的固定开销，代价是**单点失败更贵**且**漏章风险上升**；
- **分章**（一章一 agent）：定位问题最准，代价是固定开销 × 章数；
- **默认取向**：接受合章（多等一会儿，换取更低的固定开销）。所以默认合章，但**必须逐文件核验**（见第五节）。

## 七、合章为什么省（记机理，别只记结论）

省的是**两笔，叠加**才有实测的 3 倍差距：

1. **摊薄 per-agent 固定开销**（主项）。每个 agent 都要装一次系统提示、工具 schema、规范块，并重新建立上下文。按 1 章/agent 派，这笔开销被重复 N 次——早期某书 32 个 agent 就是这么烧掉的。
2. **prompt 缓存**。同一 agent 的**多轮**调用里，**前面读过的源文与写过的译文都留在上下文前缀中**，后续调用命中缓存。缓存命中价约为未命中价的 1/50（按当时供应商价）——所以合章时「重读前面章节」这一项几乎免费。

实测：某书 1 章/agent ≈ **37.5k** token/章；某扫描书 7–8 章/agent ≈ **12.2k** token/章。

**缓存按「前缀」匹配**——从第一个不同的 token 起，后面全部作废。所以**同一批 agent 必须复用同一份模板、只换路径与内容**（见 `executor-prompt-templates.md` 开头），否则前缀一开始就分叉，一笔都命中不了。

**跨 agent 的前缀共享**（可选，收益极小，别为它改结构）：把各 agent prompt 里**逐字相同**的块（格式、风格、纪律）提到最前、把路径与术语放到最后，能让公共前缀跨 agent 命中。但公共块总共约 2k token，省下的是千分之一美元级。**真正的大头是「同一 agent 内部」的多轮命中，那个只要顺序执行就天然发生。**
